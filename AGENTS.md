# AGENTS.md

Instructions for AI agents (and humans) working **on** this repository. `CLAUDE.md` is a symlink to this file.

Hodios is an open library of prompts, personas, workflows, rules and styles, compiled to every AI coding tool's native format. This repo is the source; `hermes-hq/hodios-dist` is the generated install tree (never edit it by hand).

## Commands

Node 22 (`.nvmrc`), npm workspaces.

```sh
npm ci                     # install
npm run check              # everything CI runs: typecheck, lint, format, test, build, validate
npm run build              # tsc -b for packages/schema, packages/core, packages/cli
npm test                   # vitest
npm run validate           # node packages/cli/dist/bin.js validate (needs a build)
npm run hodios -- rules    # list lint rule ids (any CLI command: npm run hodios -- <cmd>)
npm run gen:schema         # rewrite schema/*.json from packages/schema/src/schemas.ts
npm run hodios -- build    # write dist/: curated skills, plugins + marketplace, native/<tool> trees, paste, bundles; catalog/v1 with every entry
npx vitest run -u          # refresh test/golden/ after an intended adapter output change; review the diff
```

## Publishing

Three things get published, each by a different route. The full step-by-step is in [RELEASING.md](RELEASING.md); read it before releasing.

| What | Where it goes | Who publishes |
|---|---|---|
| Catalog release (content) | GitHub release `vYYYY.MMDD.N` on this repo, then `hermes-hq/hodios-dist` (install tree + `catalog/v1`), then the jsDelivr CDN | Maintainer or an agent acting for them, by hand from a green `main` |
| npm packages | `@hermes-hq/hodios-schema`, `@hermes-hq/hodios-core`, `@hermes-hq/hodios` (CLI) | Maintainer only (npm account protected by a passkey) |
| Website | hermes-ide.com/prompts rebuilds from the published catalog | Automatic after a catalog release; a maintainer triggers a rebuild if the count does not update |

**Catalog release, in order** (details and exact commands in RELEASING.md):

1. Green `main`: `npm ci && npm run check`.
2. `node tools/release/curate.mjs`, then review the `curated.txt` diff. The curated tier never exceeds its target or the 2,000 cap; new entries beyond it stay `verified`, which the CLI, the site and Hermes IDE still reach.
3. `node tools/release/readme-catalog.mjs` (README numbers and catalog section are generated; never hand-edit between the markers), commit, push.
4. `npm run hodios -- build --seq <seq> --catalog <version>` (version and seq from `tools/release/calver.mjs`).
5. Sign the manifest: `tools/release/manifest-signing.mjs sign dist/catalog/v1` with the maintainer's signing key, then verify. An unsigned or unverifiable catalog is refused by `sync-dist.mjs`, and Hermes IDE refuses it at runtime. Never print, copy or commit the private key.
6. `gh release create` with people-first notes (what is new by domain, counts; nothing internal).
7. Sync a fresh clone of `hermes-hq/hodios-dist` with `tools/release/sync-dist.mjs`, commit, push, tag.
8. Purge jsDelivr for **both** `manifest.json` and `manifest.json.minisig`; a new manifest paired with a stale signature is refused by Hermes IDE.
9. Verify from a temporary `HOME`: the CDN manifest shows the new version and its signature verifies, `npx -y @hermes-hq/hodios search <word>` finds a new entry and installs it, `npx skills add hermes-hq/hodios-dist --list` works.

**npm packages:**

- Bump only the packages whose code changed, then publish in dependency order: schema, core, cli. `packages/cli` pins core exactly, so a core change means a CLI bump too.
- `npm run build` first. Publish locally with `npm publish --access public --provenance=false` (provenance only works from CI).
- `npm whoami` failing, or a publish answering **404 Not Found** for a package that exists, means the npm login expired. Run `npm login --auth-type=web` and approve in the browser, then publish; each publish asks for one passkey approval.
- Check `npm view <package> version --prefer-online`; a new version can take a minute to appear.

**Content waves** (many new entries at once): plan batches of about 25 entries grouped by domain, check every planned id against the library first, then write each batch and have an independent reviewer check it against the quality bar before it lands. A batch that needs a new category waits until the vocabulary change that adds it is on `main`; land vocabulary changes first, on their own. After a wave, cut a catalog release so the CLI, the site and Hermes IDE see it.

## Rules for changes

- **Entry format:** see `CONTRIBUTING.md` and the three examples under `library/`. Run `npm run build && npm run validate` after every content change; fix every error by its rule id (`PS0NN`).
- **Never author computed fields:** `works_in`, `packs`, `quality`, `tested_on`, `hash`, `created`, `updated`, `license`.
- **Text only:** no `scripts/`, no `allowed-tools`, no `` !`cmd` `` shell injection, no download-and-run commands, no hidden Unicode.
- **No positional placeholders** (`$1`, `$ARGUMENTS`). Use named `{{arg}}` declared in `args`.
- **Fill the facets honestly** (`stack`, `stage`, `requires`, `inputs`, `output`, `tags`). They decide who sees an entry first; a wrong stack hides it from the people it is for.
- **Ids are forever.** Never rename or delete a released id; add the old id to the successor's `aliases`.
- **`packages/core` stays isomorphic:** no `node:` imports there; file access belongs in the CLI.
- **Public repo:** never commit personal data, local paths, emails, tokens or internal URLs.
- **Commits and PRs:** work on a branch, open a PR, wait for `check` and `dco` to pass. Squash merge only. Every commit needs a DCO `Signed-off-by` from the accountable human; an agent only adds it when that human has told it to commit under their identity.
- Keep diffs small and on-task. Do not reformat files you did not change.
