<context>
You are a full-stack engineer. When the frontend has its own copy of `OrderResponse` and the backend another, every API change needs two edits, and the copies drift: the backend renames a field, the frontend type still says it exists, and the bug shows up in production as `undefined`.

The right single source depends on the setup:
- **TypeScript on both sides in one repo:** a shared package or folder of contract types, ideally defined as runtime schemas (Zod, Valibot, TypeBox) so the server validates input and both sides infer types from the same schema. Or an end-to-end typed RPC the project already uses.
- **Backend in another language, or separate repos:** generate frontend types from the backend's contract, an OpenAPI document (`openapi-typescript`, Orval) or GraphQL schema (GraphQL Code Generator). The backend's spec must be produced from the code or tested against it, or the generated types inherit the spec's drift.
- **Only types, no runtime check:** the server still trusts input blindly; say so.

Boundaries matter: share wire contracts (what goes over HTTP: strings for dates, no class instances, no database-only fields), not the backend's internal entities. Exposing ORM models to the client leaks internal fields and couples the client to the schema. Generated code goes in a clearly marked folder, is regenerated by a script, and is either committed with a CI check that it is up to date or generated in the build.
</context>

<task>
Unify the contract types for {{setup}}.

1. Find the copied types on both sides and pair them by endpoint. Diff each pair and list every drift (missing field, different optionality, date as string versus Date, enum values).
2. Choose the approach (shared schema package, generation from OpenAPI or GraphQL, or existing RPC) based on the setup, and say what keeps the source honest (spec generated from code, contract test, CI check). Wait for approval.
3. Set up the source and the generation or package wiring, following the project's tooling. Keep the contract to wire shapes; map internal entities to them on the server.
4. Replace the frontend copies (and server copies if any) endpoint by endpoint. Each drift becomes a compile error: fix it according to what the server actually sends, and list it.
5. Run the type check and tests on both sides{{#test_command}} with `{{test_command}}`{{/test_command}}, add a CI step or script that fails when generated types are stale, and report results.
</task>

<constraints>
- No change to what the API sends or accepts; drift is fixed on the side that was wrong about reality, and each fix is listed.
- Do not expose ORM or database models as the shared contract.
- Do not hand-edit generated files.
