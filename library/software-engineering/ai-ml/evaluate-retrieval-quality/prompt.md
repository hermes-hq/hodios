<context>
When RAG answers are wrong, teams tweak the prompt, but most failures happen earlier: the right passage was never retrieved. Measuring retrieval on its own, with a labelled set of queries and their relevant chunks, shows whether a change to chunking, embeddings, hybrid search or reranking actually helped. The set must look like real traffic (short keyword queries, long questions, typos, identifiers, other languages) and include queries with no answer in the corpus. Labels tied to chunk ids break when chunking changes, so label at document or section level, or keep a mapping. Questions generated by an LLM from the passages themselves are easy (they reuse the passage's words) and inflate scores; use them only to top up real queries, and mark them.
</context>

<task>
Build a retrieval evaluation for: {{retriever}}

Query sources: {{query_sources}}

1. Read the retriever code and how results are identified (chunk ids, document ids, sections).
2. Query set: collect 50 to 300 queries, mostly real, stratified by type (lookup, identifier, paraphrase, multi-part, multilingual or typo, unanswerable). Mark synthetic ones. Remove personal data from logged queries.
3. Labelling: for each query, the relevant documents or sections (graded if useful: highly relevant, partly relevant), at a level that survives re-chunking. Describe the labelling guide and, if possible, have two people label a sample and report agreement. Unanswerable queries have no relevant items.
4. Metrics: recall@k at the k the generator receives and at a larger k, MRR, and nDCG if labels are graded; for unanswerable queries, the top score distribution, to help set a not-found threshold. Report overall and per query type.
5. Write the evaluation script: load the query set, call the retriever, compute metrics, write a per-query results file listing misses with the retrieved items, and compare against a saved baseline run.
6. Run it on the current retriever and report baseline numbers and the worst query types.
7. Explain how to use it: run on every retrieval change, the minimum improvement that counts given the set size, and how to keep the set fresh with new real queries.
</task>

<constraints>
- Keep retrieval metrics separate from answer metrics; do not use answer correctness as a proxy for retrieval.
- State how small sample sizes limit conclusions (a few queries changing flips a percentage point).
- Do not label using the retriever's own outputs alone; that bakes in its blind spots.
