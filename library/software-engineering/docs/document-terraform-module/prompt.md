<context>
A module's consumers decide from its README whether it fits and how to call it. The input and output tables are best generated by terraform-docs from `description` fields, so the real work is writing good descriptions in `variables.tf` and `outputs.tf` (units, allowed values, what the default implies) and the prose terraform-docs cannot produce: what the module creates and does not, opinionated defaults (encryption, public access blocked), a minimal and a realistic example, provider and Terraform version constraints, permissions needed to apply it, and upgrade notes for changes that force resource replacement or need `moved` blocks or state moves. Readers get burned most by undocumented replacements, inputs whose defaults are insecure or costly, and examples that reference a source or version that does not exist.
</context>

<task>
Document the module at `{{module_path}}` for consumers who use it via {{consumers}}.

1. Read every `.tf` file: resources and data sources created, variables with types, defaults and validations, outputs, `required_providers` and `required_version`, and any `moved` blocks. Read the changelog and git tags if present.
2. Add or improve `description` on every variable and output: meaning, units, allowed values, and the effect of the default. Do not change types, defaults or logic.
3. Write the README prose: purpose, what it creates, what it does not manage, security and cost-relevant defaults, and IAM or permissions needed to apply.
4. Write a minimal example and a realistic example using the consumers' source format with a placeholder version, and add or update an `examples/` folder only if the repo already uses one.
5. Add terraform-docs injection markers (`<!-- BEGIN_TF_DOCS -->` and `<!-- END_TF_DOCS -->`) and, if terraform-docs is available, run it to generate the requirements, providers, inputs and outputs tables. Otherwise write the tables by hand and note how to regenerate them.
6. Write upgrade notes for breaking changes you can find (renamed inputs, resources that will be replaced, `moved` blocks).
7. Run `terraform fmt -check` and `terraform validate` on the module if the tools are available. Never run `plan` against real accounts or `apply`.
</task>

<constraints>
- Descriptions and tables must match the code.
- Do not change variable types, defaults, validations or resources.
- Do not invent registry paths or version numbers; use placeholders.

</constraints>
